# LifeGameHermes
## Техническое задание

**Персональная AI-среда вокруг Hermes Agent**  
Версия 1.0 · 4 октября 2026 года  
Стек: Hermes Agent · Nuxt · Fastify · SQLite · Tauri 2.x

> **Hermes думает и действует как агент. LifeGame организует контекст, интерфейс и управляемые действия в окружении пользователя.**

Документ определяет целевую архитектуру, функциональные требования, ограничения и последовательность реализации. Он предназначен для поэтапной разработки одним разработчиком, в том числе с помощью coding agents.

**Статус:** исходная спецификация для реализации. Код существующего проекта и установленный у пользователя Hermes в рамках подготовки документа не проверялись. Возможности внешних инструментов сверены с официальной документацией; фактическая совместимость должна быть подтверждена на этапе E0.

**Владелец продукта:** Александр.  
**Рабочее название:** LifeGameHermes, далее — LifeGame.  
**Основной формат сопровождения:** Markdown в репозитории; DOCX — версия для чтения и обсуждения.

# 1. Назначение и границы продукта

## 1.1. Цель

Создать красивую, настраиваемую и переносимую персональную среду, в которой пользователь управляет своим рабочим и личным контекстом: комнатами, проектами, задачами, заметками, фокус-сессиями, музыкой и запуском приложений. Hermes остаётся главным AI-агентом и единственным владельцем агентной логики.

Ключевой результат: пользователь открывает LifeGame, выбирает контекст, видит нужные инструменты и одним явным действием подготавливает окружение. Он может обратиться к своему Hermes, не объясняя заново выбранную комнату и проект.

## 1.2. Базовые условия

- Один пользователь, одно локальное рабочее пространство и одна основная установка LifeGame в MVP. Поддержка нескольких вкладок нужна; multi-user и синхронизация устройств не нужны.
- Основная платформа локальных действий — macOS, поскольку в сценариях используется Alfred. Конкретная архитектура процессора и минимальная версия macOS фиксируются на E0, а не предполагаются.
- Hermes устанавливается и обслуживается отдельно. Он может находиться на том же компьютере либо на доверенном удалённом сервере. UI всегда работает с ним через LifeGame backend.
- Без доступного Hermes сохраняются локальные функции: Rooms, задачи, заметки, Focus, Timeline и разрешённые действия на устройстве. AI-функции показывают недоступность, а не вымышленные результаты.

## 1.3. Что не создаётся

LifeGame не реализует собственные agent loop, LLM routing, память пользователя, RAG-платформу, систему subagents, редактор кода, универсальный workflow engine или альтернативу Hermes Skills/MCP. Внутренний журнал событий и очередь доставки LifeGame не являются новой AI-памятью или новым агентным планировщиком.

В первой версии также отсутствуют облачный аккаунт, обязательный hosted backend, PostgreSQL, Redis, marketplace плагинов, мобильное приложение и фоновый сбор всей активности пользователя.

## 1.4. Продуктовые принципы

**Контекст вместо множества чатов.** Room определяет представление и текущий контекст, но не создаёт нового агента при каждом переключении.

**Предсказуемые действия без LLM.** Открытие приложения, запуск заранее настроенного Alfred workflow и старт Focus не должны требовать AI-запроса.

**Прозрачность вместо магии.** UI различает сохранение данных, отправку команды, завершение внешнего действия и AI-интерпретацию. «Hermes получил данные» не означает «долговременная память гарантированно обновлена».

**Сначала ежедневная полезность.** Work, Today, Capture и запуск окружения важнее графов памяти, сложной аналитики и рейтингов качества жизни.

# 2. Зафиксированные архитектурные решения

## 2.1. Разделение ответственности

| Слой | Чем владеет | Чем не владеет |
| --- | --- | --- |
| Hermes Agent | AI-рассуждение, агентные сессии, история разговоров, Skills, tools, MCP, подключённая память и агентные задания | Layout виджетов, состояние Rooms, настройки интерфейса LifeGame |
| LifeGame Core / Fastify | Доменные данные, HTTP API, разрешения LifeGame, Scenes, Focus, Timeline, интеграция с Hermes | LLM loop, собственная AI-память, копия всей истории Hermes |
| Nuxt UI | Отображение, формы, навигация, локальные черновики, визуальные состояния | Прямой доступ к SQLite, API-ключ Hermes, выполнение shell-команд |
| Device Runtime | Разрешённые действия на текущем устройстве и диагностика их доступности | Агентное принятие решений и произвольное выполнение команд из UI |
| Tauri 2.x | Desktop lifecycle, окно, native capabilities, запуск backend-процесса | Вторая реализация доменной логики и второй владелец SQLite |

Hermes документирует собственную память, поиск по сессиям, Skills, автоматизации и делегирование. Эти возможности используются через интеграцию, а не переносятся в LifeGame. [S01]

## 2.2. Обязательные ограничения

**ARCH-01.** Nuxt обращается только к LifeGame API/SDK. Из компонентов запрещены запросы к Hermes с его ключом и импорты серверных модулей.

**ARCH-02.** Только Fastify-процесс открывает рабочую SQLite-базу LifeGame. Tauri SQL plugin не используется для параллельного доступа к той же базе.

**ARCH-03.** Backend — модульный монолит. Device Runtime в MVP является модулем этого процесса. Выделение отдельного daemon допускается только при появлении удалённого Core или нескольких устройств.

**ARCH-04.** LifeGame не изменяет внутреннюю БД Hermes и не читает её напрямую. Интеграция использует поддерживаемые интерфейсы установленной версии.

**ARCH-05.** Смена Room сама по себе не запускает приложения, не закрывает их, не отправляет сообщение Hermes и не начинает Focus. Для этого есть отдельное действие «Начать работу» или запуск Scene.

**ARCH-06.** Не существует глобального пользовательского shell endpoint. Scene ссылается на зарегистрированные действия; текст заметки, ответ AI или импортированный JSON не может стать исполняемым кодом.

**ARCH-07.** Room, Hermes profile, Hermes conversation и FocusSession — разные сущности. Их нельзя связывать правилом «одна комната = один отдельный Hermes».

## 2.3. Источники истины

| Данные | Источник истины | Допустимое хранение в LifeGame |
| --- | --- | --- |
| Rooms, layouts, задачи, цели, заметки | SQLite LifeGame | Полное доменное состояние |
| Текущий контекст | SQLite LifeGame | Версия состояния и снимки для операций |
| Разговор и точный текст сообщений | Hermes | Ссылки; временный UI-кэш без второй постоянной истории |
| AI-память, Honcho и другие memory providers | Hermes и его конфигурация | Статус доступности, но не независимая копия памяти |
| Итог Focus, сгенерированный Hermes | Производный артефакт LifeGame | Текст, происхождение, версия, время и ссылки на источники |
| Статус внешнего приложения | Device provider / ОС | Последнее наблюдение со временем проверки |

# 3. Режимы запуска и технологическая основа

## 3.1. Web-first / локальная разработка

```text
Browser -> Nuxt UI -> LifeGame Fastify -> SQLite
                              |
                              +-> Hermes API
                              +-> Device Runtime -> Alfred / OS
```

В development Nuxt и Fastify работают отдельными процессами. Запросы UI к `/api/v1` проходят через настроенный dev proxy. В локальной production web-сборке Fastify раздаёт статический frontend и API с одного origin.

Nuxt используется как клиентское приложение с `ssr: false`. Серверные бизнес-функции в `server/api` Nuxt не размещаются. Для desktop формируются статические assets; отдельный Nitro server не требуется. Официальная инструкция Tauri для Nuxt предусматривает статический frontend без серверного SSR. Путь результата сборки должен быть проверен для выбранной версии, а не скопирован из случайного примера. [S04]

## 3.2. Будущая desktop-сборка

```text
Tauri host
  +-> WebView: bundled Nuxt assets
  +-> managed sidecar: Fastify + Node runtime -> SQLite
                                      |
                                      +-> external Hermes
                                      +-> local Device Runtime
```

Tauri не исполняет Node.js backend автоматически. В дистрибутив должен входить проверенный runtime/sidecar для целевой платформы. Tauri поддерживает упаковку внешних binaries и требует учитывать target architecture. [S05, S06]

Hermes не включается в первый desktop installer: пользователь подключает уже установленный агент. Установка и обновление Hermes из LifeGame — отдельная будущая возможность.

## 3.3. Технологические решения

| Область | Основное решение |
| --- | --- |
| Frontend | Nuxt 4.x, Vue, TypeScript strict; Pinia для клиентского состояния |
| Backend | Fastify 5.x, TypeScript strict; Node.js 24 LTS как стартовая ветка |
| Storage | SQLite 3.x, Drizzle ORM и `better-sqlite3` как стартовый вариант |
| API contracts | JSON Schema / TypeBox и совместимый Fastify type provider; OpenAPI из тех же схем |
| Обновления UI | HTTP + SSE; WebSocket не нужен до подтверждённого сценария |
| Monorepo | pnpm workspaces; один lockfile |
| Тесты | Vitest, Fastify `inject`, Playwright; отдельные native smoke tests |
| Desktop | Tauri 2.x; точный patch и совместимые plugins фиксируются на E0/E7 |

Node.js 24 относится к LTS-веткам в проверенной таблице релизов. Fastify документирует type providers, а Drizzle — поддержку SQLite-драйверов. Это не заменяет проверку конкретной комбинации пакетов и native packaging. [S08, S09, S10, S11]

**Правило версий:** не использовать плавающий `latest` в воспроизводимых сборках. На E0 зафиксировать точные версии, Hermes release/commit и OS/architecture в `docs/compatibility.md`. Не брать prerelease ORM автоматически вслед за текущими примерами документации. Если native driver не проходит packaging spike, заменить его отдельным ADR до разработки слоя хранения.

# 4. Структура репозитория и границы модулей

## 4.1. Целевая структура

```text
lifegame/
  apps/
    ui/                       # Nuxt
    api/                      # Fastify composition root
    desktop/                  # Tauri: появляется на E7
  packages/
    contracts/                # DTO, schemas, event contracts
    domain/                   # use cases and domain rules
    database/                 # schema, repositories, migrations
    hermes-client/            # verified Hermes adapter
    device-runtime/           # action providers and policy
    sdk/                      # typed HTTP/SSE client
  integrations/
    hermes-mcp/               # optional bridge, after read-only MVP
  presets/
    rooms/
    scenes/
  docs/
    superpowers/specs/
    superpowers/plans/
    adr/
    compatibility.md
  tests/
    contract/
    e2e/
    fixtures/
```

Структура задаёт границы, а не требует создать все каталоги в первый день. Отдельный npm package на каждую сущность не нужен. Первые тестируемые модули могут находиться внутри `apps/api/src/modules` и извлекаться без изменения публичных контрактов.

## 4.2. Направление зависимостей

`UI -> SDK -> contracts`; `Fastify routes -> application use cases -> repositories/providers`. Domain не должен импортировать Nuxt, Tauri или Fastify request/reply. Серверная композиция подставляет реальные repositories, Hermes adapter и Device providers.

Внутри backend use cases используют явные интерфейсы. Например, выполнение Scene не знает деталей AppleScript; оно получает результат от ActionProvider. Не создавать универсальную provider-платформу для замены Hermes: достаточно конкретного Hermes adapter с тестовыми doubles.

## 4.3. Обязательные инженерные соглашения

- Миграции и API contracts хранятся в Git. Секреты, пользовательская база, логи и private assets — вне репозитория.
- Общие команды `dev`, `build`, `typecheck`, `lint`, `test`, `test:e2e` должны появиться на E1 и быть описаны в README. Их наличие и успешность не предполагаются до реализации.
- UI imports проверяются на отсутствие `database`, `device-runtime`, `node:*` и server-only кода.
- Каждое изменение интерфейса сопровождается обновлением DTO, схемы, API docs и contract tests. Тестовые заглушки не являются доказательством совместимости с реальным Hermes.

# 5. Доменная модель и правила состояния

## 5.1. Базовые сущности

| Сущность | Назначение | Основные поля |
| --- | --- | --- |
| Workspace | Единственная локальная среда пользователя в MVP | `id`, `name`, `timezone`, `locale`, `revision` |
| Room | Сохранённый контекст и набор UI-поверхностей | `id`, `slug`, `title`, `kind`, `contextDefaults`, `revision`, `archivedAt` |
| WorkspaceState | Текущий общий контекст открытой среды | `workspaceId`, `roomId`, `projectId`, `taskId`, `activeFocusId`, `revision` |
| Project | Рабочий или личный проект | `id`, `title`, `status`, `description`, `goalId`, `revision` |
| Task | Минимальная задача LifeGame | `id`, `title`, `roomId`, `projectId`, `status`, `priority`, `dueDate` |
| Goal | Цель, образ желаемого результата, следующий шаг | `id`, `title`, `description`, `status`, `targetDate`, `nextAction`, `revision` |
| WidgetInstance | Экземпляр встроенного виджета | `id`, `roomId`, `type`, `config`, `schemaVersion`, `revision` |
| RoomLayout | Раскладка виджетов по breakpoint | `roomId`, `breakpoint`, `positions`, `revision` |

## 5.2. Сущности действий и интеграции

| Сущность | Назначение | Основные поля |
| --- | --- | --- |
| Scene | Версионированная последовательность известных действий | `id`, `title`, `steps`, `schemaVersion`, `revision`, `enabled` |
| DeviceBinding | Локальное сопоставление alias с приложением или workflow | `deviceId`, `alias`, `provider`, `config`, `revision` |
| SceneRun | Конкретная попытка запуска Scene | `id`, `sceneId`, `sceneRevision`, `planHash`, `status`, `actor`, `deviceId` |
| SceneStepRun | Состояние одного шага | `runId`, `stepId`, `status`, `startedAt`, `finishedAt`, `errorCode` |
| FocusSession | Период фокусированной работы | `id`, `roomId`, `projectId`, `taskId`, `status`, `startedAt`, `endedAt` |
| CaptureItem | Быстро сохранённая запись | `id`, `text`, `kind`, `roomId`, `projectId`, `aiState`, `createdAt` |
| HermesBinding | Связь комнаты/проекта с существующей беседой | `id`, `connectionId`, `profileRef`, `remoteSessionId`, `roomId`, `projectId` |
| HermesOperation | Ссылка на отправленную внешнюю операцию | `id`, `bindingId`, `remoteRunId`, `contextSnapshot`, `deliveryState` |

## 5.3. Вспомогательные записи

`Event` хранит доменное событие; `CommandReceipt` — idempotency key и результат команды; `DeliveryJob` — доставку конкретной записи или запроса summary; `IntegrationConfig` — несекретную конфигурацию и ссылку на секрет; `Asset` — метаданные локального вложения. `Approval` хранит одноразовое разрешение на точный план Scene. Не создавать для этих сущностей отдельные микросервисы.

Рабочие таблицы вводятся миграциями вместе с функциями соответствующего этапа. Таблицы будущих интеграций заранее не создаются.

## 5.4. Инварианты данных

**DATA-01.** Идентификаторы локальных сущностей — UUID. Идентификаторы Hermes хранятся как непрозрачные строки. Поля API — `camelCase`, колонки БД — `snake_case`.

**DATA-02.** Все timestamps — UTC; для UI используется IANA timezone из настроек/ОС. `dueDate` без времени хранится как календарная дата, а не как «полночь UTC». Часовой пояс не захардкожен.

**DATA-03.** В одном Workspace может быть не более одной активной или приостановленной FocusSession. Ограничение обеспечивается транзакцией и уникальным частичным индексом, а не только состоянием кнопки.

**DATA-04.** Связь с Hermes уникальна по `connectionId + profileRef + remoteSessionId`. Архивация Room или Project не удаляет беседу Hermes.

**DATA-05.** Изменение `WorkspaceState`, события и idempotency receipt выполняется атомарно. Ошибка записи не должна оставлять UI с подтверждённым несохранённым состоянием.

**DATA-06.** Изменения редактируемых сущностей используют `revision` и optimistic concurrency. При конфликте сервер возвращает `409`; UI предлагает обновить состояние, а не молча затирает другую вкладку.

**DATA-07.** Room задаёт логический контекст, но не является доказанной границей доступа AI-памяти. Для строгой изоляции нужны отдельно проверенные настройки Hermes; в MVP такая изоляция не обещается.

## 5.5. Снимок контекста

Для каждой AI-операции создаётся неизменяемый snapshot: `workspaceId`, `roomId`, `projectId`, `taskId`, `focusSessionId`, `capturedAt`, `contextRevision`, разрешённые краткие описания. Snapshot не содержит credentials и полных локальных путей по умолчанию.

Переключение комнаты во время ответа не меняет контекст уже запущенной операции. Новое сообщение использует новый snapshot. Одновременные вкладки согласуют общий `WorkspaceState` по revision; черновики сообщений остаются локальными каждой вкладке.

# 6. Rooms и пользовательские сценарии

## 6.1. Набор стартовых Rooms

| Room | Назначение | Состав |
| --- | --- | --- |
| Today | Кратко показать, что требует внимания | Приоритеты, задачи, активный Focus, Capture, быстрые Scenes, Hermes status |
| Work | Подготовить окружение и работать над выбранным проектом | Project selector, текущая задача, launcher, Focus, заметки, Hermes panel |
| HSE | Отдельный контекст деятельности HSE | Задачи и дедлайны, ссылки, материалы, заметки, связанная беседа |
| Goals | Визуальное пространство целей | Карта желаний, изображения, собственные цитаты, цели и следующие действия |
| Settings | Управление средой, а не жизненный контекст | Hermes connection, устройства, разрешения, themes, экспорт, backup, diagnostics |

HSE рассматривается как пользовательский контекст без предположений о его организационной или учебной структуре. Календарь, внешние учебные системы и документы подключаются отдельными интеграциями после уточнения источника.

## 6.2. REQ-ROOM: управление комнатами

Пользователь должен создавать Room из шаблона, переименовывать, менять порядок, выбирать icon/theme, добавлять встроенные виджеты и архивировать Room. Изменения сохраняются после перезапуска.

Комнаты описываются данными. Создание новой Room из уже зарегистрированных виджетов не требует изменения frontend-кода. Новый тип виджета, напротив, требует реализации Vue-компонента и регистрации.

Пользователь видит активную Room и выбранный проект. Контекстный переключатель не должен скрывать запущенную FocusSession: при переходе из Work в Goals Focus остаётся видимым в общей панели.

## 6.3. REQ-WORK: сценарий «Начать работу»

Пользователь выбирает проект и, при необходимости, задачу. Кнопка «Начать работу» показывает план настроенной Scene: какие приложения откроются, что закроется, требуется ли подтверждение. После явного запуска UI показывает статусы шагов.

Focus стартует отдельным подтверждённым шагом либо отдельной кнопкой. Если Scene закончилась ошибкой, Focus не начинается «по предположению». Hermes получает контекст только при AI-запросе или при отдельно включённой отправке события.

LifeGame открывает существующие IDE, terminals и coding tools. Он не заменяет их, не создаёт собственный code editor и не навязывает конкретный coding agent.

## 6.4. REQ-GOALS: визуальное пространство целей

Карточка цели содержит название, описание желаемого результата, статус, необязательную дату, изображение и следующий шаг. Связанный Project может показывать вклад в цель, но прогресс не рассчитывается как псевдообъективная оценка жизни.

Карта желаний — композиция локальных изображений, текстовых карточек и целей. На первом этапе достаточно управляемой grid-раскладки; бесконечный canvas и автоматический граф связей не входят в MVP. Загруженные изображения должны работать offline и попадать в backup вместе с данными.

# 7. Система виджетов

## 7.1. REQ-WIDGET: registry и контракт

Каждый встроенный виджет имеет `type`, отображаемое название, `schemaVersion`, схему `config`, разрешённые размеры, Vue-компонент, зависимости от capabilities и политику обновления данных. `WidgetInstance` хранит только конфигурацию и размещение, но не функцию или код компонента.

Registry поставляется с приложением. Импорт Room разрешает только известные типы и поля. Произвольный JavaScript, HTML, удалённые Vue-компоненты и пользовательские схемы для компиляции Fastify не допускаются. Fastify отдельно предупреждает, что validation schemas нужно рассматривать как код приложения. [S08]

## 7.2. Каталог и очередность

| Виджет | Минимальное поведение | Этап |
| --- | --- | --- |
| Quick Actions / Launcher | Кнопки известных Scenes и app aliases | E2: mock; E4: реальные действия |
| Tasks | Создать, завершить, отфильтровать по контексту | E2 |
| Current Project | Выбор проекта и текущей задачи | E2 |
| Hermes | Статус, связанная беседа, отправка сообщения | E3 |
| Focus | Start/pause/resume/finish, краткий итог | E5 |
| Capture | Быстрое сохранение текста без обязательной классификации | E5 |
| Timeline | Недавние события и фильтр контекста | E5 |
| Weather | Настраиваемая локация, время обновления, stale/offline state | E6, отдельный provider |
| Radio | Список настроенных HTTP(S)-потоков, play/pause/volume | E6 |
| Music Launcher | Открытие Яндекс Музыки или выбранного музыкального приложения | E4/E6 |
| Goal / Quote / Image | Цель, собственный текст или локальный asset | E6 |

**Яндекс Музыка:** первая реализация — launcher и, при подтверждённой возможности ОС, media controls. Авторизованный каталог, поиск и streaming через неофициальный API не являются обязательством ТЗ. Встраивание в iframe допускается только после проверки ограничений источника и безопасности.

## 7.3. Состояния и производительность

Все виджеты должны поддерживать `loading`, `ready`, `empty`, `stale`, `error`, `unavailable`. Сбой одного виджета не ломает Room. Ошибка содержит понятное действие: повторить, открыть настройки либо отключить недоступную интеграцию.

Запросы к одному ресурсу разделяют кэш и не дублируются по числу виджетов. Например, Tasks и Today summary не должны независимо опрашивать одинаковый список каждую секунду. Погода обновляется редко; пользовательские изменения приходят через domain events.

При скрытии Room фоновые опросы её виджетов приостанавливаются. Исключения — активный Focus, ongoing run и явно запущенное пользователем аудио. Смена Room не останавливает музыку; закрытие приложения не обещает продолжение воспроизведения в MVP.

## 7.4. Layout

Desktop использует адаптивную grid-систему, стартово 12 колонок; узкий экран — одноколоночную раскладку. Есть режим редактирования, перемещение, изменение размера в рамках ограничений виджета, reset layout и сохранение.

Drag-and-drop должен иметь клавиатурную альтернативу. Ошибка неизвестной версии конфигурации отображается локально в виджете; приложение не стирает несовместимые данные автоматически.

# 8. Actions, Scenes и управление приложениями

## 8.1. REQ-ACTION: детерминированные действия

Action — зарегистрированная операция Device Runtime или домена LifeGame. Её контракт содержит `id`, `provider`, input schema, capability, уровень риска, timeout, признак безопасного повтора и семантику подтверждения результата.

Стартовый набор: `app.open`, `app.quit`, `url.open`, `alfred.trigger`, `shortcut.run` при наличии provider, `focus.start`, `focus.finish`. `app.open` получает alias из доверенной конфигурации устройства, а не исполняемый путь от LLM.

Вызовы OS utilities выполняются через фиксированную программу и массив аргументов, без построения shell-строк из пользовательского ввода. Наличие аргументов само по себе не считается безопасностью: provider проверяет их смысл, разрешённые значения и target.

## 8.2. REQ-SCENE: выполнение Scene

Scene — короткий последовательный список Action. В MVP нет произвольных условий, циклов, вложенных графов, cron, параллельных веток и AI-планирования. Входные параметры Scene валидируются по заранее определённому контракту.

Последовательность запуска:

1. **Preview:** разрешить aliases, проверить provider/capabilities, получить snapshot шагов и рисков. Действия на устройстве не выполняются.
2. **Approval:** при необходимости получить явное согласие на конкретный `planHash`, `sceneRevision` и `deviceId`. План действует 5 минут; изменение конфигурации делает его недействительным.
3. **Run:** атомарно создать SceneRun и idempotency receipt; выполнять шаги по порядку, отображая фактические статусы.
4. **Finish:** сохранить итог и краткое событие Timeline. Ошибка по умолчанию останавливает следующие шаги.

На одном устройстве в MVP выполняется не более одной изменяющей окружение Scene одновременно. Повторный запуск с тем же `Idempotency-Key` возвращает исходный Run. Новый ключ во время конфликтующего Run получает `409`.

## 8.3. Семантика результата

| Статус | Значение |
| --- | --- |
| `pending` / `running` | Шаг ещё не выполнен / выполняется |
| `succeeded` | Provider подтвердил результат в рамках своего контракта |
| `dispatched` | Внешняя система приняла команду, завершение не наблюдается |
| `failed` | Получена подтверждённая ошибка |
| `unknown` | После разрыва или перезапуска невозможно подтвердить исход |
| `skipped` / `cancelled` | Шаг не запускался из-за политики / отмены |

SceneRun использует `queued`, `running`, `completed`, `dispatched`, `failed`, `cancelled`, `interrupted`. Если хотя бы один успешно отправленный шаг имеет только подтверждение отправки, финальный результат всей Scene — `dispatched`, не `completed`.

Команда отмены не является rollback. Уже открытые приложения не закрываются автоматически. При перезапуске незавершённая Scene получает `interrupted`; потенциально неидемпотентные шаги не повторяются автоматически.

## 8.4. Alfred

Alfred предоставляет External Trigger через AppleScript или URL Handler. Для вызова нужны workflow bundle ID и trigger ID. [S13]

Provider хранит эти идентификаторы в локальной доверенной конфигурации. Простой вызов trigger подтверждает только отправку. Нельзя показывать «все приложения закрыты», если workflow не вернул проверяемый результат.

Для MVP разрешены два варианта: отображать «Команда отправлена» либо разбить критичные операции на наблюдаемые Action. Callback-протокол от workflow — необязательное расширение с run/step ID и одноразовым токеном. Следующий шаг, требующий именно завершения предыдущего, запрещён для dispatch-only provider без callback.

## 8.5. Закрытие программ

«Завершить рабочее окружение» закрывает только явно выбранные приложения. Принудительное завершение процессов, удаление файлов, очистка системных кэшей и выключение компьютера не входят в стартовый набор.

Обычное завершение приложения может встретить диалог несохранённых изменений. Provider не должен обходить его или автоматически переходить к force kill. Scene не обещает «очистить RAM»: её результат — управление приложениями, а не доказанное улучшение памяти системы.

Закрытие программ требует подтверждения плана, даже если открытие этих же программ ранее было разрешено. Допустимое будущее исключение — осознанная пользовательская политика для конкретной Scene, не глобальное разрешение AI закрывать всё.

# 9. Focus, Capture, задачи и Timeline

## 9.1. REQ-FOCUS

FocusSession связывается с Room и необязательными Project/Task. Состояния: `active -> paused -> active -> completed`; допускается `cancelled`. Pause/resume фиксируются timestamps и интервалами. Браузерный `setInterval` отвечает только за визуальное обновление, а не за источник длительности.

Активный UI отправляет heartbeat раз в 30 секунд; Core сохраняет `lastSeenAt`, не создавая Timeline event на каждый heartbeat. Разрыв больше 2 минут помечает интервал для review при восстановлении, но не завершает Focus автоматически.

После reload UI восстанавливает сессию из backend. После сна устройства, длительного разрыва heartbeat или неожиданного завершения приложения сессия отмечается `needsReview`. Пользователь может скорректировать интервал; система не приписывает всё время отсутствия «глубокой работе». История исправлений сохраняется.

Finish немедленно сохраняет длительность, заметки и пользовательский итог. Генерация AI summary — отдельная операция, не блокирующая сохранение. Статусы summary: `not_requested`, `pending`, `ready`, `failed`. Можно повторить запрос вручную.

## 9.2. REQ-CAPTURE

Capture доступен из каждой Room и command palette. Пользователь вводит текст и сохраняет его без выбора категории. Room/Project подставляются из snapshot, но могут быть изменены перед сохранением.

Порядок строгий: сначала commit в SQLite, затем необязательная отправка Hermes. В случае недоступности AI запись остаётся доступной. Передача текста агенту по умолчанию требует явного действия «Разобрать с Hermes»; автоматическую обработку можно отдельно включить в настройках.

Hermes предлагает тип записи, краткий итог и возможную задачу. Его ответ не перезаписывает оригинал. Создание задачи из предложения требует подтверждения пользователя. UI не пишет «сохранено в долговременную память», если внешняя система этого не подтверждала.

## 9.3. REQ-TASK

Минимальная задача содержит название, состояние `todo | doing | done | cancelled`, приоритет и необязательный срок. Поддерживаются создание, редактирование, завершение и привязка к Room/Project. Повторяющиеся задачи, subtasks, зависимости и двусторонняя синхронизация с внешними trackers отложены.

Количество незавершённых задач и календарные сроки рассчитываются детерминированно. Hermes можно попросить предложить приоритеты, но предложенный порядок не становится фактом без принятия пользователем.

## 9.4. REQ-TIMELINE

Timeline показывает реальные события LifeGame: `room.entered`, `project.selected`, `scene.started`, `scene.finished`, `focus.started`, `focus.paused`, `focus.finished`, `capture.created`, `task.completed`, `goal.updated` и результаты явно инициированных AI-операций.

Event содержит `id`, возрастающий `sequence`, `type`, `schemaVersion`, `occurredAt`, `actor`, `entityRef`, `roomId`, `projectId`, `correlationId`, небольшой безопасный `payload`. Событие записывается в одной транзакции с изменением домена. Публикация SSE выполняется после commit. `actor` выводится из аутентифицированного principal и не принимается как доверенное поле от клиента.

Timeline — журнал приложения, не full event sourcing. Текущее состояние читается из доменных таблиц; replay всех событий для запуска приложения не требуется. В Timeline не пишутся token deltas, полный текст разговоров, секреты и постоянные screenshots.

Фильтры: день, Room, Project, тип события. Длительность работы берётся из Focus, а не выводится из времени между открытием приложений. Импорт событий всех внешних Hermes-каналов — отдельное расширение, не гарантированное покрытие MVP.

# 10. Интеграция с Hermes

## 10.1. Проверенная поверхность и ограничения

Официальная документация Hermes API описывает bearer authentication, capability discovery, сессии и Runs API с SSE. Ниже перечислены ориентиры для adapter; они должны быть проверены на конкретной установке пользователя. [S02]

| Возможность | Документированный интерфейс Hermes |
| --- | --- |
| Проверка возможностей | `GET /v1/capabilities` |
| Список / создание сессий | `GET /api/sessions`, `POST /api/sessions` |
| История | `GET /api/sessions/{id}/messages` |
| Отправка agent run | `POST /v1/runs` |
| Статус / поток | `GET /v1/runs/{id}`, `GET /v1/runs/{id}/events` |
| Остановка / approval | `POST /v1/runs/{id}/stop`, `POST /v1/runs/{id}/approval` |

**Важно:** это не маршруты LifeGame API. Весь перевод запросов, статусов и ошибок находится в `hermes-client`. Документация текущего upstream не доказывает, что эти функции присутствуют у пользователя.

## 10.2. REQ-HERMES: capability-first adapter

После настройки endpoint backend проверяет соединение и capabilities, сохраняет диагностический snapshot без секретов. UI показывает только проверенные функции. Для отсутствующего endpoint используется `unsupported`, а не фиктивный успешный ответ.

Для MVP нужны: authenticated connection, восстановление/создание беседы, отправка сообщения и получение ответа. Предпочтительный transport — Runs API с отдельной подпиской. Если установленная версия поддерживает другой достаточный интерфейс, fallback описывается и тестируется отдельным контрактом. Shell-парсинг CLI и чтение private DB не являются fallback.

Approval UI включается только после проверки полного round trip. Неподдерживаемое действие нельзя автоматически одобрять. Запрос остановки отображается как «Останавливается» до подтверждения Hermes; он не означает мгновенное прекращение внешних операций.

## 10.3. Беседы, profile и память

Пользователь выбирает одну основную Hermes connection/profile. В Work беседа может быть привязана к Project; в HSE — к Room. Он может продолжить существующую беседу или явно создать новую. Новая беседа не создаётся на каждый вход в Room.

Установленные Honcho и другие memory providers продолжают управляться Hermes. LifeGame не меняет их конфигурацию без отдельного действия. Общий агент/profile не гарантирует автоматически одинаковую память во всех каналах: выбранную стратегию идентичности и scope необходимо проверить на E0/E3.

Для сохранения устойчивой идентичности пользователя adapter должен изучить поддерживаемый механизм session key установленной версии. `remoteSessionId` нельзя без проверки использовать как постоянный идентификатор личности. Перед включением обмена данными тестируется продолжение беседы и переход между двумя беседами в одном профиле.

## 10.4. Передача контекста

Backend получает актуальное состояние из SQLite, проверяет присланную UI `contextRevision` и формирует ограниченный snapshot. При устаревшей revision возвращается `409`, чтобы UI не отправил сообщение в неожиданном контексте.

В AI-запрос передаются только выбранные идентификаторы, названия и краткие данные, необходимые для задачи. Полное содержимое Room, заметки других контекстов и содержимое файлов не прикладываются автоматически.

Context не должен заменять базовый system prompt Hermes, удалять его Skills или изменять глобальные permissions. Пользовательский текст считается данными, а не административной инструкцией. Изменения контекста не порождают оплачиваемый AI-вызов сами по себе.

## 10.5. Streaming, восстановление и delivery

SSE parser поддерживает границы chunks, многострочные сообщения, keepalive и неизвестные типы событий. Потеря соединения не создаёт новый run. Adapter сначала запрашивает статус уже известного `remoteRunId`, затем восстанавливает UI.

Возможность replay проверяется по контракту конкретного интерфейса. Если она отсутствует, UI запрашивает snapshot/историю; не обещается восстановление каждого token delta.

При неизвестном результате отправки AI-запроса создаётся состояние `delivery_unknown`. Автоповтор допустим только при проверенной upstream idempotency либо после подтверждения отсутствия операции. Иначе пользователь получает выбор проверить/повторить, а не скрытую двойную работу агента.

Одна локальная беседа имеет не более одного исходящего незавершённого turn из LifeGame. Существующий Hermes run хранится как внешняя ссылка; LifeGame не создаёт собственный agent scheduler вокруг него.

## 10.6. Hermes -> LifeGame

После рабочего MVP предусматривается небольшой MCP bridge. Hermes документирует подключение MCP servers, в том числе через stdio. [S03]

Первая версия bridge — read-only: `get_context`, `get_today`, `list_projects`, `get_scene_status`. Следующий шаг — `create_capture` и запрос предварительного плана Scene. Агент не получает права произвольно выполнять все локальные действия.

Bridge вызывает те же use cases Fastify, что и UI, с отдельным scoped credential. Он не открывает SQLite напрямую. Approval на системные действия остаётся в LifeGame и не может быть удовлетворён фразой агента «пользователь согласен».

Hermes hooks можно подключить позднее для внешних событий. Сам webhook не гарантирует доставку, полноту истории или отсутствие дублей; для расширения нужны authentication, event ID, deduplication и наблюдаемая ошибка доставки. [S14]

# 11. Контракты LifeGame API

## 11.1. Общие правила

Все прикладные маршруты используют префикс `/api/v1`. JSON-ответы валидируются теми же общими contracts, по которым формируется клиентский SDK. Streaming, assets и health имеют явно описанные исключения по формату.

Успешный JSON: `{ "data": ..., "meta": { "requestId": "..." } }`. Ошибка: `{ "error": { "code": "...", "message": "...", "requestId": "...", "retryable": false } }`. Stack trace и секретные details в UI не возвращаются.

Стандартные коды: `400 VALIDATION_ERROR`, `401 UNAUTHORIZED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 REVISION_CONFLICT`, `409 IDEMPOTENCY_CONFLICT`, `422 CAPABILITY_UNAVAILABLE`, `429 RATE_LIMITED`, `502 HERMES_ERROR`, `503 HERMES_UNAVAILABLE`.

Списки используют cursor pagination: `limit` по умолчанию 50, максимум 100, `nextCursor` или `null`. Domain mutations принимают `Idempotency-Key`, если повтор может создать сущность или внешний эффект. Обновления существующего состояния требуют `expectedRevision`.

## 11.5. Два различных потока событий

**Domain SSE** передаёт сохранённые LifeGame Events. `sequence` используется как cursor; дубликаты допустимы на transport-уровне и отбрасываются клиентом. При устаревшем cursor сервер требует resync и выдаёт новое состояние, а не имитирует непрерывную историю.

**Hermes SSE** передаёт состояние внешнего run. Он не записывает каждый токен в таблицу Events. SDK должен поддерживать streaming `fetch` с заголовком Authorization там, где нужен bearer token; ключи запрещено добавлять в URL ради удобства EventSource.

## 11.6. Idempotency и транзакции

`CommandReceipt` уникален по `principal + operation + key`; хранит hash входа и результат/ID операции. Тот же ключ с другим payload возвращает `409`. Стартовый срок хранения receipts — 7 дней; это настройка LifeGame, не обещание срока хранения Hermes.

Receipt и локальные изменения создаются одной транзакцией. Внешняя команда никогда не выполняется внутри длительной SQLite-транзакции. После принятия внешнего эффекта и аварии между ним и локальным commit результат считается неизвестным до reconciliation, а не автоматически повторяется.

# 12. SQLite, миграции, резервирование и переносимость

## 12.1. Хранилище

SQLite находится в user data directory, выбранном конфигурацией/desktop host. Оно не размещается в Git, `node_modules`, каталоге приложения или общей сетевой папке. Только один LifeGame Core обслуживает конкретный data directory.

Стартовые настройки: `foreign_keys = ON`, WAL, ограниченный `busy_timeout` и короткие транзакции. Для приоритета сохранности заметок стартово использовать `synchronous = FULL`; менять на более слабую durability только по измерениям и ADR.

WAL допускает одновременные readers и writer, но не несколько одновременно пишущих транзакций; shared-memory механизм не предназначен для сетевой файловой системы. Это причина не считать файл SQLite механизмом синхронизации устройств. [S12]

Индексы обязательны для `events(sequence)`, событий по контексту/времени, задач по Room/Project/status, Capture по времени и уникальных idempotency keys. Частичный unique index обеспечивает одну незавершённую FocusSession.

## 12.2. Миграции

Миграции нумеруются, проходят review и тестируются на новой базе и предыдущем поддерживаемом schema version. При запуске Core сначала проверяет схему, делает необходимый backup и только затем начинает обслуживать запросы.

Если база новее приложения, запуск останавливается с понятной ошибкой. Автоматический downgrade и удаление пользовательских данных ради старта запрещены. Для rollback приложения используется совместимая версия и проверенный backup, а не набор неподтверждённых down migrations.

JSON-поля Room, Scene и Widget имеют свой `schemaVersion` и отдельные преобразования. Seed presets создаются один раз или импортируются по запросу; обновление приложения не перезаписывает пользовательские layouts.

## 12.3. Backup и восстановление

Backup выполняется через корректный SQLite backup mechanism, а не копированием только `.db` из активно работающего WAL-хранилища. SQLite предоставляет Online Backup API. [S15]

Архив включает consistent database snapshot, assets, manifest с версиями и checksums. Секреты по умолчанию не включаются. Перед restore проверяются формат, размер, checksums, совместимость и отсутствие path traversal; затем Core закрывает текущую базу и атомарно заменяет данные с сохранением прежней копии.

Первый release должен пройти реальный restore test: после восстановления доступны Rooms, задачи, Capture, Focus и локальные изображения. Тест проводится на отдельном data directory.

## 12.4. Portable export отличается от backup

**Backup** восстанавливает собственную установку. **Portable export** переносит выбранные Rooms, widgets и Scenes как конфигурацию для другого человека.

Portable export не содержит Hermes keys, личную историю, локальные абсолютные пути, machine ID и tokens. Scene использует app aliases; на новом устройстве пользователь сопоставляет их своим приложениям. Неизвестные providers отмечаются `unavailable`.

Импорт показывает preview, новые сущности и конфликты. Он никогда не запускает Scene и не выдаёт права imported action автоматически. Стандартное действие при конфликте — создать копию с новым ID, не перезаписать существующую запись молча.

# 13. Безопасность и приватность

## 13.1. REQ-SEC: local-first не означает отсутствие authentication

Core слушает `127.0.0.1` по умолчанию, не `0.0.0.0`. Прикладные API защищены. Проверяются Host и browser Origin; CORS allowlist закрытый. «Запрос пришёл на localhost» не является достаточным разрешением управлять приложениями.

**Локальный web-режим:** одноразовый pairing code выдаётся через локальный терминал, вводится пользователем и обменивается на HttpOnly session cookie. Cookie имеет `SameSite=Strict`; для HTTPS включается `Secure`. На loopback HTTP допускается только явно ограниченный local mode. State-changing запросы дополнительно проверяют Origin и CSRF token. Код pairing имеет короткий срок и rate limit.

**Desktop:** Tauri host запускает sidecar, передаёт ему случайный process token через private pipe/stdin и сообщает UI endpoint/token через ограниченный IPC bootstrap. Token хранится только в памяти, обновляется при перезапуске backend и не попадает в URL, argv или localStorage.

**Remote Core:** не входит в MVP. Его нельзя включить простой заменой bind address без TLS, нормальной authentication и отдельной модели доверия устройствам.

## 13.2. Секреты

Hermes API key хранится на стороне Core: для разработки допустим закрытый `.env` вне Git; для desktop — OS-backed secret storage или другой отдельно проверенный vault adapter. SQLite хранит только secret reference.

В frontend `runtimeConfig.public`, SSR payload, analytics, debug exports и screenshots не должны попадать credentials. Диагностический экспорт редактирует headers, query parameters и connection strings. Проверка наличия секрета отображается как boolean, не как маскированная строка с реальными фрагментами.

## 13.3. Permissions

| Действие | Начальная политика |
| --- | --- |
| Читать разрешённый текущий контекст | Разрешено аутентифицированному UI; MCP — по scope |
| Создать локальную заметку по прямой команде | Разрешено; валидация и audit event обязательны |
| Открыть зарегистрированное приложение | Разрешено после настройки binding пользователем |
| Запустить неизвестный/импортированный workflow | Запрещено до review и настройки |
| Закрыть приложения | Подтверждение точного плана |
| Выполнить произвольный shell / force kill | Недоступно в MVP |
| Изменить permissions или secrets через Hermes | Запрещено |
| Передать новую категорию личных данных агенту | Явное включение или одноразовое подтверждение |

Approval ограничивается операцией, arguments, device, версией плана и временем. Его нельзя повторно использовать после изменения Scene. Права LifeGame и approvals Hermes — разные проверки; одна не должна автоматически обходить другую.

## 13.4. UI и импорт как границы доверия

Markdown sanitization обязательна; произвольный HTML из ответа Hermes не исполняется. Ссылки имеют allowlist схем; `javascript:` и неизвестные custom schemes запрещены. Внешний контент не получает native Tauri permissions.

Assets импортируются с лимитами размера/типа; SVG не исполняется как произвольный документ. Для MVP безопаснее разрешить raster images и не поддерживать active document formats. Пути assets выдаются по ID после проверки доступа, не по произвольному filesystem path.

Room isolation и permission scopes в UI не способны ограничить другие независимые tools Hermes, уже разрешённые в его конфигурации. Безопасность полного окружения зависит также от настроек самого Hermes; LifeGame гарантирует только собственные entry points.

## 13.5. Приватность

Автоматическая telemetry и отправка crash reports отключены по умолчанию. Автосбор screenshots, clipboard, браузерной истории и активных окон не производится. Weather location вводится пользователем либо получается после отдельного согласия; точная геолокация не требуется.

В Settings должны быть показаны: что хранится локально, какие данные уходят Hermes, какие providers доступны и как удалить/экспортировать LifeGame data. Удаление данных LifeGame не обещает удаления уже переданной информации у внешнего memory provider.

# 14. Требования к UI и качеству работы

## 14.1. Визуальная система

Интерфейс строится вокруг Rooms и постоянной доступности Hermes, а не вокруг обязательного полноэкранного чата. На каждом экране доступны текущий контекст, command palette, Capture, активный Focus и состояние подключения.

Требуются light/dark themes, единые design tokens, согласованные spacing/radius/typography и аккуратные empty states. Визуальная «комнатность» достигается композицией и акцентами, а не множеством независимых несовместимых интерфейсов.

Детальный visual design выполняется отдельным этапом внутри E2/E6. Это ТЗ не фиксирует конкретную библиотеку UI-компонентов и не требует имитировать чужой dashboard.

## 14.2. Доступность и управление

Все основные действия доступны клавиатурой. `Cmd/Ctrl+K` открывает command palette внутри приложения; глобальное сочетание назначается отдельно и не перехватывает Alfred/системный launcher по умолчанию. Есть видимый focus indicator и учёт `prefers-reduced-motion`.

Целевой контраст обычного текста — не ниже 4.5:1; цвет не является единственным обозначением статуса. Modal confirmation озвучивает действие и возвращает focus инициатору. Desktop UI должен оставаться usable при ширине 1024 px; узкий web layout — при 390 px.

## 14.3. Ошибки, offline и отзывчивость

Любая внешняя функция имеет timeout и состояние unavailable. Отказ Hermes не блокирует загрузку Rooms. Потеря backend-соединения показывает явный banner; приложение не подтверждает сохранение до ответа сервера. Локальный текстовый draft восстанавливается после refresh, но не считается записанным в БД.

UI не делает бесконечный retry для изменяющих команд. Для read-only запросов допускается ограниченный exponential backoff; для Actions и AI runs действуют правила idempotency/reconciliation.

## 14.4. Целевые показатели

| Показатель | Начальная цель и способ проверки |
| --- | --- |
| Переключение уже загруженной Room | p95 до 200 ms, без ожидания Hermes |
| Локальный CRUD и чтение страницы до 100 записей | p95 до 250 ms на контрольном устройстве |
| Холодный старт desktop до usable UI | До 5 s без запуска/ожидания Hermes |
| Нагрузка для baseline | 20 Rooms, 200 widgets, 5 000 tasks/captures, 50 000 Events |
| Idle-поведение | Нет постоянного polling скрытых widgets и busy loops |
| Память | Измеряется отдельно для UI/Core; память Hermes и открытых приложений не приписывается LifeGame |

Эти значения — стартовые цели. На E0/E7 фиксируются hardware, build mode и метод измерения. Изменять цели без измерений нельзя, но они не являются утверждением о готовой производительности.

# 15. Упаковка в Tauri 2.x

## 15.1. Desktop lifecycle

Tauri host определяет data directory, создаёт process token и запускает один Core sidecar. Core выбирает свободный loopback port, открывает БД, выполняет миграции и сообщает readiness по private channel. Только после этого UI получает bootstrap connection.

При повторном запуске приложения активируется существующее окно. Создавать два Core для одной базы запрещено: дополнительно нужен data-directory lock и понятная ошибка, если Core уже запущен другим способом.

Обычное закрытие главного окна в первой desktop-версии завершает LifeGame после предупреждения об активных локальных операциях. Tray/background mode — opt-in расширение, не скрытая семантика default close.

## 15.2. Остановка и восстановление

При выходе Core прекращает принимать новые команды, завершает/фиксирует локальные операции, закрывает SSE и БД. Host останавливает только принадлежащий LifeGame процесс. Внешний Hermes, IDE, Alfred и программы пользователя не завершаются вслед за окном.

Если host аварийно завершился, sidecar должен обнаружить закрытие управляющего канала и выйти после bounded grace period. После crash sidecar UI предлагает восстановление; новый token требует reconnect всех клиентов. Не допускаются бесконечный restart loop и незаметные orphan processes.

Закрытие UI не считается отменой уже принятого Hermes run. Его фактическое состояние определяется при следующем подключении; отдельно можно явно запросить stop.

## 15.3. Native security

Tauri capabilities задаются для конкретного окна и необходимых команд. Frontend не получает `shell` с произвольными arguments, полный filesystem или разрешения на remote origins. Desktop IPC занимается bootstrap и ограниченными native функциями, а не дублирует Actions API. Tauri документирует granular capabilities и permissions. [S07]

Origin WebView, CSP и loopback connection должны быть проверены в packaged build. Dynamic port не является причиной отключать CSP. Любые необходимые исключения ограничиваются loopback и не дают удалённым страницам native permissions.

## 15.4. Packaging acceptance

Desktop package содержит Nuxt assets, Core, Node runtime, требуемые native modules и миграции. Он должен запускаться на чистой целевой машине без глобально установленного Node.js. Если используется `better-sqlite3`, native binary проверяется для каждой публикуемой архитектуры.

Tauri сам по себе не делает bundle из Node-зависимостей; стратегия упаковки подтверждается spike на E0. До desktop release проверяются подпись/notarization для выбранного способа распространения, writable data paths, обновление базы и отсутствие secrets в package. Auto-updater отложен до отдельного безопасного механизма обновлений.

## E0. Проверить основу до большой разработки

**Цель:** убрать риски, способные изменить архитектуру.

**Работы:** зафиксировать Hermes version/commit, endpoint, authentication и capabilities; проверить одну беседу, продолжение истории, run status/stream, ошибку соединения и остановку, если она нужна; проверить фактическую конфигурацию memory scope. Подготовить throwaway packaging spike: статический Nuxt экран, Fastify health, одна SQLite запись, packaged Tauri + Core на основной архитектуре без зависимости от системного Node.

Проверить Alfred External Trigger на тестовом безопасном workflow. Зафиксировать, даёт ли вызов только dispatch или observable completion. Определить доступные приложения и aliases без закрытия рабочих программ пользователя.

**Артефакты:** `docs/compatibility.md`, ADR по Hermes transport и Node/SQLite packaging, список capabilities с `supported/unsupported/not-tested`, отдельный отчёт spike. Точные версии фиксируются только после реального теста.

**Приёмка:** повторяемый минимальный round trip с реальным Hermes; SQLite читается после перезапуска spike; packaging не требует глобального Node; недоступные возможности перечислены. Если критичный тест не прошёл — скорректировать adapter/packaging до E1, не маскировать проблему mock-ответом.

**Не входит:** полноценный UI, универсальный bridge, интеграция всех Hermes tools, автоматическая установка Hermes.

## E1. Фундамент приложения

**Цель:** получить запускаемую, защищённую и тестируемую среду.

**Работы:** создать pnpm workspace, Nuxt SPA, Fastify composition root, contracts и SDK. Подключить выбранный SQLite driver, migrations, Workspace, auth, error envelope, configuration validation и structured logs с redaction. Реализовать минимальный domain Event/receipt mechanism без будущих бизнес-модулей.

Настроить production static serving, development proxy, тестовую БД и fixtures. Добавить version/health diagnostics без секретов. Ввести dependency boundary checks и CI для уже созданных scripts.

**Приёмка:** чистая установка создаёт БД; restart сохраняет данные; API без credentials отклоняется; несовместимая схема даёт понятную ошибку; startup без Hermes показывает usable shell. Команды typecheck/lint/test/build реально запускаются и их результаты сохраняются в отчёте этапа.

**Не входит:** AI-чат, локальное управление приложениями, визуальный polish всех Rooms.

## E2. Полезный UI без AI-зависимости

**Цель:** сделать настраиваемую среду, которой можно пользоваться до интеграций.

**Работы:** реализовать App Shell, navigation, command palette, Rooms CRUD/archive, контекст и revisions, Projects, Tasks, widget registry и layout persistence. Создать Today и Work presets. Реализовать встроенные Tasks, Current Project и безопасные placeholders недоступных Actions/Hermes.

Настроить theme tokens, responsive grid, empty/error states и клавиатурное управление. Переключение Room меняет только контекст и представление.

**Приёмка:** пользователь создаёт Room, добавляет несколько виджетов, меняет layout и получает то же состояние после restart. Две вкладки не затирают изменения без сообщения о конфликте. Tasks работают при выключенном Hermes. Неизвестный виджет не ломает Room.

**Не входит:** произвольные пользовательские плагины и новый тип виджета из исполняемого JSON.

## E3. Hermes как основное AI-окно

**Цель:** подключить существующего агента без копирования его инфраструктуры.

**Работы:** реализовать настройки connection, проверку capabilities, список/привязку бесед, message composer, run submission, status и SSE. Добавить snapshot текущего контекста, явные ошибки unsupported/unavailable, reconnect и delivery_unknown.

Реализовать stop/approval только для подтверждённых возможностей. Проверить отсутствие Hermes key в UI bundle, сети browser->Hermes, logs и экспорте. UI показывает названия исходного контекста у текущего run.

**Приёмка:** сообщение из Work приходит реальному Hermes с корректным контекстом; ответ streaming отображается; reload не создаёт дубль; продолжение использует ту же беседу. Переход в HSE во время ответа не меняет snapshot текущего run. Недоступный Hermes не блокирует Tasks и Rooms.

**Не входит:** редактирование Hermes config, собственный memory explorer, AI-маршрутизатор провайдеров и coding IDE.

## E4. Запуск рабочего окружения

**Цель:** сделать LifeGame повседневным launcher/control surface.

**Работы:** реализовать Action registry, Device bindings, capability discovery, Scenes CRUD, preview, approvals, idempotency, step statuses и cancel. Первые providers: безопасное открытие приложений/URL и Alfred trigger. Закрытие программ — отдельное подтверждаемое действие.

Создать пользовательскую Scene для Work из aliases, не из захардкоженных путей Александра. Реализовать проверку неизвестных результатов, single-run lock и interrupted recovery. Показать фактическое отличие `dispatched` от `completed`.

**Приёмка:** Work Scene запускается одной подтверждённой командой; двойное нажатие не создаёт двойную работу. Неустановленный Alfred отображается как unavailable. Переключение Room само не запускает Scene. Конфигурация, изменённая после approval, отклоняется. App quit не превращается в force kill при ошибке.

**Контрольная точка:** уже полезная версия — комнаты, задачи, Hermes и запуск окружения.

## E5. Focus, Capture и связная история — функциональный MVP

**Цель:** завершить основной ежедневный цикл: начать работу, сохранить мысли, закончить и восстановить контекст.

**Работы:** реализовать Focus с pause/resume/recovery, Capture с локальным commit, Timeline и filters. Добавить задаваемый пользователем AI summary Focus и разбор выбранной Capture. Минимальная DeliveryJob хранит только конкретную операцию передачи, ограниченные retries и unknown state; не реализует cron или общую agent orchestration.

Ввести backup/restore для текущих данных и сценарий сохранения незаконченного draft. Привязать пользовательские события к Project/Room. Сводка Today остаётся работоспособной без AI.

**Приёмка:** заметка сохраняется при недоступном Hermes; Focus переживает reload; после сна/краша спорный интервал требует review; повторное завершение не удваивает длительность. AI-итог помечен как сгенерированный и связан с исходными заметками/сессией. Backup реально восстанавливает рабочую среду.

**Граница MVP:** E0–E5 завершены, критические тесты раздела 17 пройдены, отсутствуют скрытые дублирующие AI-системы.

## E6. HSE, Goals и персонализация

**Цель:** расширить рабочую оболочку до персональной среды.

**Работы:** создать HSE preset на тех же Tasks/Notes/Links, добавить Goals, image/quote widgets и asset storage. Реализовать Weather через выбранный provider, Radio через настроенные потоки и Music Launcher. Для каждой интеграции документировать внешние требования, недоступность и privacy.

Добавить portable configuration export/import и read-only MCP bridge к Hermes. Write-capabilities через bridge включать только отдельной задачей с теми же approval tests, что у UI. Не делать свободное выполнение Scene из любого текста агента.

**Приёмка:** HSE не является отдельной копией приложения; Goals доступны offline, изображения входят в backup. Неработающее радио не ломает UI; смена Room не обрывает запущенное аудио. Weather показывает возраст данных. Импорт Room не запускает приложения. Read-only MCP не может изменить permissions или выполнить Action.

**Не входит:** полноценный клиент Яндекс Музыки, банковские данные, приватные учебные API без отдельного исследования.

## E7. Desktop на Tauri 2.x

**Цель:** упаковать уже работающий продукт без переписывания Core.

**Работы:** добавить desktop host, packaged static UI, проверенный sidecar, bootstrap token, data-directory lock, process lifecycle и минимальные capabilities. Проверить loopback access, CSP, native permissions и app signing для способа распространения.

Реализовать понятное поведение close/restart, диагностику backend crash и отсутствие orphan processes. Проверить packaged database migration и backup перед обновлением. Tray/autostart/global shortcuts — только после стабильного базового lifecycle.

**Приёмка:** app запускается на чистой целевой машине без Node; один app instance соответствует одному Core; повторный запуск не создаёт второй writer. Закрытие LifeGame не останавливает Hermes и IDE. Assets и БД находятся в writable user data directory. Desktop проходит те же доменные сценарии, что web.

**Не входит:** обязательное включение Hermes/Python в installer и multi-platform release без отдельных тестов каждой платформы.

## E8. Подготовка open-source release

**Цель:** дать другому человеку воспроизводимо запустить и настроить LifeGame.

**Работы:** привести README и setup guide, добавить example config, demo presets без личных данных, compatibility matrix, architecture/extension guide, troubleshooting, backup/restore guide и SECURITY policy. Проверить dependency licenses, отсутствие чужого кода с несовместимыми условиями и отсутствие secrets в Git history/package.

Добавить CI install/build/test из чистого checkout, release notes и versioned migrations. Document offline mode, отдельную установку Hermes, необязательность Alfred и ограничения неподдерживаемых integrations. Лицензию собственного кода согласовать до публикации; стартовый кандидат — MIT.

**Приёмка:** другой разработчик следует README без знания личной машины автора; настраивает endpoint Hermes, создаёт Room и запускает безопасную Scene через доступный provider. Экспорт пресетов не содержит путей/ключей/личных заметок. Claims в README соответствуют реально проверенным платформам.

**Публикация:** подготовка файлов не означает автоматическую публикацию репозитория или release. Внешняя публикация выполняется только отдельным явным действием владельца.

# 17. Тестирование и приёмочные сценарии

## 17.1. Стратегия тестов

**Unit:** инварианты контекста, Focus time accounting, риск Action, вычисление plan hash, revisions и переходы состояний.

**Integration:** Fastify routes через `inject`, реальные SQLite migrations/transactions, duplicate commands, concurrency, backup/restore. В тестах действий использовать безопасный fake provider; реальные OS smoke tests запускаются отдельно и не закрывают пользовательские приложения.

**Contract:** схемы SDK/API, Hermes capabilities и fixtures настоящих response shapes. Real-Hermes smoke test выполняется отдельно с тестовой беседой и явно разрешённым безопасным сообщением; платные вызовы не запускаются скрыто в обычном CI.

**E2E:** ключевые пользовательские маршруты в web UI; desktop lifecycle и native permissions — дополнительно в packaged app. Playwright браузерный тест сам по себе не подтверждает корректность Tauri WebView и macOS automation.

## 17.3. Общий Definition of Done

Задача считается завершённой, когда реализовано наблюдаемое поведение, обновлены contracts/migrations, добавлены relevant tests и действительно запущены нужные проверки. Должны быть проверены error/empty/offline states и отсутствие секретов в diagnostic output.

Отчёт этапа содержит: что изменено, какие команды реально выполнены, их результат, ручные проверки, оставшиеся ограничения и решение о следующем этапе. «Код выглядит корректно» и «mock прошёл» не заменяют evidence реальной интеграции.

Изменение рабочего протокола Hermes, публикация, перезапись пользовательских данных и опасные OS-действия не прячутся внутри обычной задачи UI. Для них нужен явно указанный scope и отдельный acceptance test.

# 18. Отложенные возможности и контроль объёма

## 18.1. После рабочего MVP

Memory Explorer может показывать только поддерживаемые источники/объяснения Hermes, а не вторую базу памяти. Полноценный knowledge graph не создаётся автоматически из Events.

Local Bridge daemon появляется, когда Core действительно переносится на другой компьютер. Нужны pairing, device identity, подписанные/scoped команды, reconnect и отдельная модель угроз. В MVP достаточно локального Device Runtime.

Дополнительные комнаты Reflect, Media, Health и Finance создаются по конкретным сценариям. Для чувствительных источников и внешних аккаунтов нужна отдельная спецификация privacy/access; существование Room не означает наличие интеграции.

## 18.2. Не добавлять без отдельного ADR/ТЗ

- Multi-user, cloud sync, PostgreSQL, Redis, очереди внешнего брокера и Kubernetes.
- Marketplace с установкой произвольного JS/Node кода, universal workflow designer и собственный cron для AI.
- Full coding IDE, произвольный terminal в WebView, параллельный AI Council и свой агентный runtime.
- Полный Яндекс Музыка client, пассивный activity tracking и «оценка качества жизни».

Эти ограничения не запрещают развитие. Они защищают основной продукт: красивую управляемую среду вокруг уже существующего Hermes.

# 19. Риски, решения перед стартом и правила изменений

## 19.1. Главные риски

| Риск | Мера |
| --- | --- |
| Документация Hermes опережает установленную версию | Capability discovery, pinned baseline, real contract smoke tests |
| Начинается строительство второго Hermes | Ownership matrix; новый AI engine требует пересмотра scope |
| Node/native SQLite сложно упаковать | Packaging spike E0 до реализации большого storage layer |
| Room воспринимается как изолированная память | Явное предупреждение; memory/profile scope проверяется отдельно |
| Запуск Scene незаметно закрывает работу | Preview, exact approval, graceful quit, no force kill |
| Crash после внешнего эффекта создаёт дубль | Idempotency receipt, unknown state, reconciliation вместо слепого retry |
| Разрастается конфигурационный/plugin framework | Только встроенный registry, aliases и последовательные Scenes |
| Повреждение/потеря локальной базы | Один Core, миграции с backup, restore test, safe data directory |

## 19.2. Решения, которые уже можно принять

Стек и разделение UI/Core/Hermes зафиксированы. Исходная архитектура — local-first modular monolith, статический Nuxt, SQLite с одним владельцем, Scenes без AI и Tauri как desktop host. Отдельные репозитории, remote daemon и cloud не нужны для старта.

Набор Rooms — Today, Work, HSE, Goals плюс Settings. Work — единая комната программирования с выбором Project внутри. Конкретные IDE/coding tools выбирает пользователь через app aliases.

## 19.3. Что должен установить E0

Точная версия Hermes и реально доступные API; OS/CPU основной машины; exact runtime/library versions; способ упаковки Node/SQLite; выбранный локальный secret storage; доступные Alfred workflows. Это технические результаты проверки, а не причины останавливать подготовку проекта.

Weather provider, радиостанции, музыка, окончательные визуальные tokens и лицензия собственного кода не блокируют E1–E5. Их решения фиксируются на соответствующем этапе.

## 19.4. Работа с AI-разработчиком

Канонический файл рекомендуется положить в `docs/superpowers/specs/2026-10-04-lifegamehermes-design.md`. Планы этапов — в `docs/superpowers/plans/`. ТЗ — целевая спецификация, не отчёт об уже написанном коде.

Перед реализацией очередного этапа агент должен прочитать ТЗ и существующий репозиторий, сопоставить план с фактическим кодом, назвать файлы и acceptance tests. Не требуется заново исследовать всю архитектуру при каждой маленькой задаче, но нельзя игнорировать более свежие ADR.

**Стартовая задача:** выполнить только E0. Зафиксировать совместимость и ограничения, подготовить ADR и evidence. Не создавать production memory engine, универсальную plugin-систему и весь UI одновременно. После E0 составить конкретный план E1 на основании реально проверенного окружения.

# 20. Приложения

## 20.1. Пример Room-конфигурации

Пример показывает формат данных, а не готовую реализацию schema. `widgets.type` должен ссылаться на встроенный registry; поля проходят валидацию. Room не содержит исполняемого кода и API-ключей.

```json
{
  "schemaVersion": 1,
  "slug": "work",
  "title": "Work",
  "kind": "work",
  "contextDefaults": { "domain": "development" },
  "widgets": [
    { "type": "current-project", "config": {} },
    { "type": "tasks", "config": { "scope": "current-project" } },
    { "type": "hermes", "config": { "binding": "current-context" } },
    { "type": "focus", "config": {} },
    { "type": "launcher", "config": { "sceneAliases": ["start-work"] } }
  ],
  "onEnter": { "runScene": false }
}
```

## 20.2. Пример переносимой Scene

Scene использует aliases. Их сопоставление с установленными приложениями хранится только на устройстве. Этот пример ничего не закрывает и не запускает AI; открытие Room остаётся отдельным контекстным действием.

```json
{
  "schemaVersion": 1,
  "alias": "start-work",
  "title": "Start Work",
  "steps": [
    {
      "id": "open-editor",
      "action": "app.open",
      "input": { "appAlias": "editor" }
    },
    {
      "id": "open-terminal",
      "action": "app.open",
      "input": { "appAlias": "terminal" }
    },
    {
      "id": "open-browser",
      "action": "app.open",
      "input": { "appAlias": "work-browser" }
    }
  ],
  "failurePolicy": "stop"
}
```

Отдельная Scene с `alfred.trigger` должна иметь пометку dispatch-only, пока не реализована обратная связь. Не объединять несколько dispatch-only steps так, будто их завершение гарантированно последовательно.
